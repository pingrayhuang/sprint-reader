02 · Before vs After

Sprint Reader改變了什麼？

傳統做法 現況
  • 60 分鐘影片，需連續完整觀看
  • 完訓率當 KPI，沒人管有沒有記住
  • 所有人看同一份材料，沒有個人化
  • 行為數據（閱讀時間、分心次數）完全不記錄
  • 合規訓練 = 成本中心
Sprint Reader 本專案
  • 7 分鐘限時閱讀 + 後端蓋章，防止快速跳過
  • 閱讀完立即測驗，觸發主動提取，留存率提升
  • 錯題回溯原始卡片，弱點圖譜個人化
  • Visibility API 記錄 tab 切換，行為數據化
  • 合規訓練 = 風險預警資產
MA 跨部門視野：這個設計讓法遵部（知識留存 KPI）、教育訓練部（個人化課程）、資料部（行為 panel）、IT（部署）同時受益——正是 MA 輪調要接觸的四個 function。

04 · Design Decisions

為什麼這樣設計？5 個關鍵決策

① 為什麼用 Visibility API 記錄 tab 切換？
面試官問「業務員切到 Line 看訊息怎麼辦」——答案是：Visibility API 偵測到 tab 切走，前端自動暫停計時並送 POST /api/sprint/telemetry，後端累積 tab_switch_count。這個數字未來可以作為「注意力風險指標」餵給 AI 做個人化課程推薦。
② 為什麼用後端蓋 timestamp，不用前端 timer？
前端 JS timer 可以被開發者工具竄改。session_manager.py 在 POST /start 時記錄 start_timestamp，在 POST /complete 時記錄 end_timestamp。就算前端 timer 被改，後端的實際閱讀時間不會被騙。符合金融業稽核需求的「不可竄改性」。
③ 為什麼用 SQLite 而不是 PostgreSQL？
Demo 階段 SQLite 夠用，且零部署成本——一個 .db 檔案就是整個資料庫，面試前 python3 init_db.py 重建，一分鐘搞定。如果要上正式環境，只需要換 connection string，業務邏輯不用動（ORM 模式）。
④ 為什麼 P2 Quiz 用 mock UUID 而不是真正串接？
Demo 要跑通完整流程，但 P2 Quiz Engine 已經在同一個專案內實作了（quiz.py）。handoff.py 只是包裝了一個「橋接表」的概念，讓面試官看到「如果 P2 是獨立服務，你會怎麼設計介面」——這本身就是架構設計能力的展示。
⑤ 為什麼題目取自真實 PDF 而不是 AI 生成？
「JY 價值筆記」的 18 題取自人身保險業務員考試真實題庫。面試被問「題目哪來的」時，答「業務員考試真題題庫」比「AI 生成」更有說服力，也代表內容的可信度。

09 · Interview Prep

面試官最常問的四個問題

業務員切到 Line 看訊息，你怎麼處理？
Visibility API 偵測到 document.hidden，前端暫停 timer 並送 POST /api/sprint/telemetry，後端 tab_switch_count + 1。切回來時繼續計時。結果頁會顯示總 tab 切換次數，作為「注意力行為」指標。
你怎麼防止前端改 JS 作弊 timer？
後端 session_manager.py 在 start 和 complete 各記一個 server-side timestamp，實際閱讀時間由兩者差值決定。就算前端 timer 被改成 0，後端看到的時間不變，法遵稽核看的也是後端數字。
這三張表為什麼這樣設計？（LearningJourney_Map 是什麼？）
SprintSessions 管閱讀行為；QuizResponses 管答題記錄；兩者透過 LearningJourney_Map 橋接，代表「一次完整的學習旅程」。這個設計讓 P3（Reader）和 P2（Quiz）可以分別部署，未來也可以 N:1——同一次 Sprint 對應多個 Quiz 嘗試。
這個 demo 的具體應用情境？
業務員要考人身保險證照（150 題 / 140 分過 / 1 個月內）。這個工具把考照準備壓縮成「6 章 × 7 分鐘」的碎片化結構，同時收集閱讀行為數據。考完照後，同一套架構可轉成「在職續訓工具」——新法規推播 7 分鐘包。一次開發，兩個場景。
